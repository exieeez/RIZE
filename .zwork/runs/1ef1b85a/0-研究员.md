# Отчёт: падение Votify «при включении трека» после b52422f

## Резюме выводов

**Главный виновник — новый кроссфейд в `PlayerController.kt`.** Корутины затухания/нарастания запускаются в `scope` = `appScope` на `Dispatchers.Default` (фоновый поток) и первым же шагом обращаются к `MediaController.availableCommands`. `getAvailableCommands()` в media3 1.4.1 жёстко проверяет поток и при вызове не с главного потока бросает `IllegalStateException("MediaController method is called from a wrong thread. See javadoc of MediaController for details.")`. Проверка стоит **вне** `runCatching` (`PlayerController.kt:216`), исключение не поймано → необработанный сбой в `launch`-корутине роняет процесс. Триггер — событие `EVENT_MEDIA_ITEM_TRANSITION`, приходящее сразу после старта воспроизведения: `onEvents` → `startFadeIn()` → 1-й шаг `volumeTo(0f)` → падение через миллисекунды после «включения трека». **Обязательное условие: в настройках включён кроссфейд.** При включённом кроссфейде падение детерминированное (на каждом старте трека/переходе); при выключенном этот путь не срабатывает вообще.

**Версия «падение из-за haze-стекла» отбракована.** Байткод haze-android 0.7.3 не содержит ни одной рантайм-проверки «один источник на HazeState» или «потомок источника»; единственный `UnsupportedOperationException` относится к `android.graphics.Path` и на устройстве недостижим.

## Находки (по силе опоры)

### Н1. Точка отказа и конкретное исключение (высшая опора: код + байткод зависимости)

`android/app/src/main/java/app/votify/mobile/player/PlayerController.kt:213–217`:

```kotlin
private fun volumeTo(value: Float) {
    val c = controller ?: return
    if (!c.isConnected) return
    if (!c.availableCommands.contains(Player.COMMAND_SET_VOLUME)) return  // :216 — вне runCatching
    runCatching { c.volume = value.coerceIn(0f, 1f) }                     // :217 — внутри runCatching
}
```

Обратите внимание на асимметрию: само присваивание `c.volume` защищено `runCatching`, а чтение `c.availableCommands` — нет. По байткоду media3-session 1.4.1 (AAR из Gradle-кэша, декомпиляция `javap`): `MediaController.getAvailableCommands()` вызывает `verifyApplicationThread()`, и в классе присутствует константа-строка `"MediaController method is called from a wrong thread. See javadoc of MediaController for details."` (проверка потока вызывается ~114 раз в `MediaController.class`, в т.ч. в `setVolume`/`getVolume`/`getAvailableCommands`; в `isConnected()` её **нет** — поэтому guard на строке 215 безопасен, а обращение на 216 падает). Контракт media3: проверка потока выполняется через `Assertions.checkState` → `IllegalStateException` (класс исключения — по документированному контракту media3; остаточная неопределённость: сам `media3-common-1.4.1.aar`, где лежит `Assertions`, я вскрыть не успел, но строка сообщения подтверждена в байткоде).

### Н2. Почему код вообще оказывается в фоновом потоке (код)

`android/app/src/main/java/app/votify/mobile/player/PlayerController.kt:186–210` (оба фейда):

```kotlin
fadeJob = scope.launch {            // :189 / :201
    for (i in steps downTo 0) {
        volumeTo(i / steps.toFloat())   // :192 / :205
        delay(FADE_STEP_MS)
    }
```

`android/app/src/main/java/app/votify/mobile/VotifyApp.kt:24,79`:

```kotlin
val appScope = CoroutineScope(SupervisorJob() + Dispatchers.Default)   // :24
player = PlayerController(context = this, scope = appScope, ...)       // :79
```

`scope` у `PlayerController` — это `appScope` с **Dispatchers.Default**, поэтому тело фейд-корутин исполняется на рабочем потоке пула, а не на main. Новый кроссфейд-блок (`startFadeIn`/`startFadeOut`/`maybeStartFadeOut` + `scope.launch`) добавлен именно в b52422f — это видно из `git show b52422f` (сообщение коммита: «КРОССФЕЙД работает по-настоящему: плавное затухание… нарастание»; диф `PlayerController.kt` +250 строк).

### Н3. Почему именно «в момент включения трека» (код, чтение путей исполнения)

`PlayerController.kt:125–126`: в `onEvents`…

```kotlin
if (events.contains(Player.EVENT_MEDIA_ITEM_TRANSITION) && crossfadeEnabled) {
    startFadeIn()
}
```

Сценарий «пользователь нажал трек в списке»: `play()` (main) → `setMediaItems`/`prepare`/`play` (main, безопасно) → плеер начинает играть → приходит `EVENT_MEDIA_ITEM_TRANSITION` → `startFadeIn()` → корутина уходит на `Default` → первый шаг `volumeTo(0f)` → `getAvailableCommands()` → wrong thread → `IllegalStateException`. Т.е. вылет происходит не по клику, а через мгновение после фактического старта воспроизведения — ровно как формулирует пользователь. Второй фейд-путь (`maybeStartFadeOut` из тикера, `PlayerController.kt:164` → `startFadeOut`) уронил бы приложение примерно за `crossfadeSeconds` (по умолчанию 4 с) до конца трека; при включённом кроссфейде падение на старте маскирует этот сценарий (до конца трека дело не доходит).

### Н4. Необработанность исключения (инференс, высокая уверенность)

Это `scope.launch` без `CoroutineExceptionHandler` (в `appScope` его нет — `SupervisorJob()+Dispatchers.Default`). Непойманное исключение из `launch` с `SupervisorJob` не отменяет «соседей», но уходит в стандартный обработчик → `Thread.uncaughtExceptionHandler` → на Android это фатальный краш процесса (`FATAL EXCEPTION`). Это стандартная семантика kotlinx.coroutines — помечаю как инференс, а не как прочитанный код.

## Альтернативы (б) — с оценкой уверенности

Оценки даны **при условии, что кроссфейд включён**; если он выключен — версия 1 обнуляется, и остальные нужно перенормировать (см. явное заявление в конце).

1. **Кроссфейд → wrong-thread — ~85–90 %.** Почему высокая: механизм подтверждён на двух концах (приложение: корутина на `Default` + незащищённое чтение `availableCommands`; библиотека: проверка потока в `getAvailableCommands` и сама строка сообщения в байткоде 1.4.1); симптом («сразу при включении трека») совпадает с моментом `EVENT_MEDIA_ITEM_TRANSITION`; появился только после коммита, добавившего этот код. Остаточные ~10 %: не вскрыт `media3-common` (точная форма проверки — throw vs log) и не подтверждено, включён ли кроссфейд у пользователя.
2. **Аудио-подсистема — ~5 %.** `requestAudioPreferences`/`PlaybackService.applyAudioPrefs`/LoudnessEnhancer и живой `setAudioAttributes` — новые в b52422f. Но большинство вызовов обёрнуты в `runCatching`, а сценарий привязан к созданию сессии/старту сервиса, а не строго к «включению трека»; глубоко не аудировал (см. непроверенное).
3. **Краевые случаи shuffle-очереди — ~3 %.** `NoSuchElementException`/`coerceIn` реальны теоретически, но пути — `next()`/конец очереди, не старт.
4. **Не связано с b52422f — ~5–7 %.** Против: симптом синхронен коммиту; сетевые/серверные ошибки идут через `PlaybackException` → `onPlayerError` (который в b52422f стал *терпимее*, а не строже) и сами процесс не роняют. За: устройство/лог недоступны, исключить окружение полностью нельзя.
5. **Haze/стекло — ≤1 %, отбракована** (Н5).
